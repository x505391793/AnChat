AnChat 实机卡顿根因诊断报告

分析范围：app/src/main 全量代码  |  技术栈：Kotlin + Jetpack Compose + Room  |  日期：2026-07-27

一句话结论：卡顿与"数据量"几乎无关。三处卡顿由 两个跨页面的主线程同步 IO 热点 共同导致—— CharacterAvatar 在主线程同步解码图片（滑动卡顿头号元凶），ConfigManager 的主身份方法每次都同步读盘+JSON 解析（进入/切换卡顿）。 即便只有 10 条消息、3 个角色卡，只要带头像图、进过聊天页，每次组合都在主线程做磁盘 IO，必然掉帧。

P0 · CharacterAvatar 主线程同步解码图片 致命

app/src/main/java/com/anchat/ui/theme/CharacterAvatar.kt:46

问题代码

@Composable

    val bitmap = remember(avatarPath) { loadAvatarBitmap(avatarPath, context) }

    BitmapFactory.decodeStream(...) // <- 主线程同步 IO
}
为何卡：
  • remember 缓存生命周期 = composable 实例生命周期。LazyColumn 滑动时，item 滑出可视区被回收，滑回来时 composable 重新组合，remember(avatarPath) 重新执行 loadAvatarBitmap —— 每次滑回都重新解码同一张图。
  • 聊天页每个气泡都带头像（用户右侧 + AI 左侧），滑动时每个进入屏幕的气泡解码 1~2 张图。即使"没多少数据"，带头像时每屏几条各解码一次，累积掉帧。
  • 同步阻塞组合线程：decodeFile/decodeStream 是磁盘 IO + 解码，单次几毫秒到几十毫秒，在主线程直接造成丢帧（16ms 预算被吃掉）。
  • 跨页面放大：通讯录、对话列表、聊天页、我的页都用 CharacterAvatar，进入任一含头像的列表页首帧都要解码多个头像。

修复方案：应用级 LruCache + 异步解码

核心思路：① 解码后的 ImageBitmap 用应用级 LruCache 缓存（按 path），跨 item 生命周期存活；② 解码切到 Dispatchers.IO，不阻塞组合线程；③ 未命中时先显示默认首字母，解码完成后自动刷新。

// 新建 AvatarCache.kt（或加到 CharacterAvatar.kt 顶部）
import androidx.collection.LruCache
import androidx.compose.ui.graphics.ImageBitmap

/** 应用级头像缓存：按 avatarPath 缓存解码后的 ImageBitmap，
 *  跨 composable / LazyColumn item 生命周期存活，避免滑回重解码。 */
object AvatarCache {
    private const val MAX = 64
    private val cache = LruCache<String, ImageBitmap>(MAX)

    fun get(path: String): ImageBitmap? = cache.get(path)
    fun put(path: String, bmp: ImageBitmap) { cache.put(path, bmp) }
    fun evict() { cache.evictAll() } // 换头像/删角色时调
}
// CharacterAvatar.kt 改造
@Composable
fun CharacterAvatar(
    name: String, avatarPath: String?, size: Dp, corner: Dp = 8.dp, modifier: Modifier = Modifier
) {
    val context = LocalContext.current
    // 1) 同步取缓存：命中则零开销，不命中先 null（显示默认首字母）
    var bitmap by remember(avatarPath) {
        mutableStateOf(avatarPath?.let { AvatarCache.get(it) })
    }
    // 2) 未命中 → 异步解码（IO 线程），完成后写缓存 + 刷新
    LaunchedEffect(avatarPath) {
        if (avatarPath != null && bitmap == null) {
            val bmp = withContext(Dispatchers.IO) { loadAvatarBitmap(avatarPath, context) }
            if (bmp != null) {
                AvatarCache.put(avatarPath, bmp)
                bitmap = bmp
            }
        }
    }
    // 3) 渲染：有图显示图，无图（含加载中）显示首字母+配色
    Box(
        modifier = modifier.size(size).clip(RoundedCornerShape(corner))
            .background(if (bitmap == null) avatarColor(name) else Color.Transparent),
        contentAlignment = Alignment.Center
    ) {
        if (bitmap != null) {
            Image(bitmap = bitmap, contentDescription = name,
                modifier = Modifier.size(size), contentScale = ContentScale.Crop)
        } else {
            Text(text = avatarInitial(name), color = Color.White,
                style = MaterialTheme.typography.titleMedium)
        }
    }
}
注意：loadAvatarBitmap 内部的 Log.d（每次解码打日志）也应去掉，滑动时大量日志输出本身有开销。 另：用户上传新头像或删除角色卡后，记得调 AvatarCache.evict()，避免读到旧缓存。

P1 · ConfigManager 主身份方法同步读盘 严重

app/src/main/java/com/anchat/data/config/ConfigManager.kt:254-262

问题代码

// ConfigManager.kt —— 五个主身份 getter 全部 load() 读盘
fun getDefaultUserName(): String = load().defaultUserName
fun getDefaultUserDescription(): String = load().defaultUserDescription
fun getDefaultUserAvatar(): String = load().defaultUserAvatar
fun getDefaultUserGender(): String = load().defaultUserGender
fun getDefaultUserWechatId(): String = load().defaultUserWechatId

// load() → loadFromFile()
private fun loadFromFile(): AppConfig {
    return json.decodeFromString<AppConfig>(defaultConfigFile.readText())
    //                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    // 每次都：读整个 anchat_config.json 文件 + JSON 反序列化整个 AppConfig
}
为何卡：对比同文件里 themeMode / models / developerMode 都有 MutableStateFlow 缓存（getter 只读内存值），但主身份五个字段漏了缓存，每次调用都 load() 读盘。
  • ChatViewModel.init 里 profileOf()（ChatViewModel.kt:349）在 observeConversation.collect 回调中每次对话快照变化都被调用，内部调 getDefaultUserGender() + getDefaultUserWechatId()，非 overridden 时还会调 userName/avatar/description —— 每次对话变化 = 主线程 3~5 次文件读取 + JSON 解析。
  • MeScreen（MeScreen.kt:42-45）组合时直接同步调 4 次 getDefaultXxx() → 切到"我"栏目时主线程读盘 4 次。
  • 若用 SAF 模式（loadFromSaf），还要走 ContentResolver 打开输入流，更慢。
  • 这些方法都不是 suspend，在 viewModelScope.launch（默认 Main）里直接阻塞主线程。

修复方案：主身份字段补齐 StateFlow 缓存

与 themeMode 完全一致的模式——初始化时读一次盘，之后 getter 只读内存；写时同步流。

// ConfigManager.kt —— 仿 themeMode 的写法补齐 5 个字段
// 1) 字段
private val _defaultUserName = MutableStateFlow(load().defaultUserName)
val defaultUserNameFlow: StateFlow<String> = _defaultUserName.asStateFlow()
private val _defaultUserDescription = MutableStateFlow(load().defaultUserDescription)
private val _defaultUserAvatar = MutableStateFlow(load().defaultUserAvatar)
private val _defaultUserGender = MutableStateFlow(load().defaultUserGender)
private val _defaultUserWechatId = MutableStateFlow(load().defaultUserWechatId)

// 2) getter 改为读内存（O(1)，不再读盘）
fun getDefaultUserName(): String = _defaultUserName.value
fun getDefaultUserDescription(): String = _defaultUserDescription.value
fun getDefaultUserAvatar(): String = _defaultUserAvatar.value
fun getDefaultUserGender(): String = _defaultUserGender.value
fun getDefaultUserWechatId(): String = _defaultUserWechatId.value

// 3) persist() 里同步这 5 个流
private fun persist(mutate: (AppConfig) -> AppConfig) {
    val newConfig = mutate(load())
    save(newConfig)
    _themeMode.value = newConfig.themeMode
    _models.value = newConfig.models
    _defaultModelId.value = newConfig.defaultModelId
    _chatModelId.value = newConfig.chatModelId
    _realConversationModelId.value = newConfig.realConversationModelId
    _notificationsEnabled.value = newConfig.notificationsEnabled
    _developerMode.value = newConfig.developerMode
    _defaultUserName.value = newConfig.defaultUserName
    _defaultUserDescription.value = newConfig.defaultUserDescription
    _defaultUserAvatar.value = newConfig.defaultUserAvatar
    _defaultUserGender.value = newConfig.defaultUserGender
    _defaultUserWechatId.value = newConfig.defaultUserWechatId
}

// 4) resync() 里同样补齐
fun resync() {
    val cfg = load()
    _themeMode.value = cfg.themeMode
    // ... 其它流 ...
    _defaultUserName.value = cfg.defaultUserName
    _defaultUserDescription.value = cfg.defaultUserDescription
    _defaultUserAvatar.value = cfg.defaultUserAvatar
    _defaultUserGender.value = cfg.defaultUserGender
    _defaultUserWechatId.value = cfg.defaultUserWechatId
}
注意：构造函数里多处 MutableStateFlow(load().xxx) 会各自调一次 load()（themeMode/models/… 已有此问题）。 建议改成构造时 val initial = load() 取一次，所有字段从 initial 初始化，避免启动时多次读盘。这是顺带优化。

P2 · 列表项不稳定 lambda 导致重组 中等

ChatScreen.kt:249 / HistoryScreen.kt:118

问题代码

// ChatScreen.kt —— items lambda 里每次都新建 onDelete / onAvatarClick
items(messages, key = { it.behaviorId ?: ... }, contentType = { it.role }) { msg ->
    ChatMessageItem(
        msg = msg, ...,
        onDelete = { viewModel.deleteMessage(it) },           // 每次重组新实例
        onAvatarClick = { isUser ->                          // 捕获 conversationId
            if (conversationId != null) navController.navigate(...)
        }
    )
}
为何卡：当 messages 或顶层任一 collectAsStateWithLifecycle 变化时，ChatScreen 整体重组，items 的 content lambda 重新执行， 为每个可见项重新生成 onDelete/onAvatarClick 这两个 lambda（新实例）。 即便消息内容没变，因参数引用变了，ChatMessageItem 也会被重组。有 key 所以只影响可见项，但滑动时每帧可见项变化，叠加 P0 的图片解码，掉帧被放大。

修复方案：稳定 lambda 上提 + remember

// ChatScreen.kt —— 把不依赖每项数据的 lambda 提到 items 外面 remember
val onDelete: (String) -> Unit = remember(viewModel) {
    { viewModel.deleteMessage(it) }
}
// onAvatarClick 依赖 conversationId，用 remember(conversationId) 包
val onAvatarClick: (Boolean) -> Unit = remember(navController, conversationId) {
    { isUser ->
        val id = conversationId
        if (id != null) navController.navigate("conversation/$id?part=${if (isUser) "self" else "ai"}")
    }
}
// items 里直接传这两个稳定引用
items(messages, key = { ... }, contentType = { it.role }) { msg ->
    ChatMessageItem(msg = msg, ..., onDelete = onDelete, onAvatarClick = onAvatarClick)
}

HistoryScreen 同理：onPin/onDelete 可上提 remember(viewModel)；onClick 依赖每项 conv.id，可在 ConversationItem 内部用 remember(conv.id) 包，或保留现状（影响较小）。

P3 · 每气泡一个 SelectionContainer 轻微

ChatScreen.kt:556-557
// 每个气泡都建立独立选区上下文
CompositionLocalProvider(LocalTextToolbar provides toolbar) {
    SelectionContainer { ... }
}
为何卡：SelectionContainer 内部注册 SelectionRegistrar、维护选区手柄与手势监听。每屏十几个气泡各一份， 滑动时每个进入屏幕的气泡都要建立这套上下文，有累积开销。修好 P0 后此项基本可忽略，是锦上添花。

优化方向（可选）：把 SelectionContainer 提到 LazyColumn 外层包裹整个列表，让所有气泡共享一个选区；或在气泡未被长按激活时用普通 Text，仅长按进入选择态时切换为 SelectionContainer。当前架构改动较大，建议 P0/P1 修完后再评估。

修复优先级清单

P0 — 必须立刻修（滑动卡顿头号元凶）
  • 新建 AvatarCache（LruCache），CharacterAvatar 改为「同步取缓存 + 未命中异步解码」。
  • 解码切 Dispatchers.IO，去掉 loadAvatarBitmap 里的 Log.d。
  • 换头像/删角色后调 AvatarCache.evict()。
预期收益：聊天页滑动从"明显卡顿"→基本顺滑（无头像场景零成本，有头像场景首屏加载后顺滑）。
P1 — 强烈建议修（进入/切换卡顿）
  • ConfigManager 补齐 5 个主身份 MutableStateFlow 缓存，getter 改读内存。
  • persist() / resync() 同步这 5 个流。
  • 构造函数改为单次 load() 初始化所有字段（顺带优化）。
预期收益：进入聊天页、切到"我"栏目从主线程多次读盘→纯内存读，卡顿消失。
P2 — 建议修（减少不必要重组）
  • ChatScreen / HistoryScreen 把 onDelete/onPin 等不依赖每项数据的 lambda 用 remember 上提。
  • onAvatarClick 用 remember(conversationId) 稳定化。
P3 — 可选（锦上添花）
  • 评估 SelectionContainer 上提到列表外层或按需激活。P0 修完后此项影响很小，可暂缓。

验证方法

  • 修复后用 adb shell dumpsys gfxinfo com.anchat 看 frame stats，或 Android Studio Profiler 录制滑动帧。
  • 重点确认：滑动时主线程不再出现 BitmapFactory.decodeFile / FileInputStream.read / JSON 解析 调用栈。
  • 无头像场景（默认首字母）应完全顺滑；有头像场景首屏后顺滑、滑回零重复解码。
